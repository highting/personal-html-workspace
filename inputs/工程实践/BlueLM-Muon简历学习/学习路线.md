**学习模块 C：Muon 和 Newton–Schulz 的数学与计算量**

这是项目中需要讲得最扎实的算法部分。

先补齐这些线性代数知识：

- 矩阵乘法、转置、秩、奇异值分解。
- Frobenius 范数、谱范数、条件数。
- 正交矩阵与矩形矩阵的半正交性。
- 极分解，以及它与奇异值分解的关系。

再理解 Muon：它对动量形成的矩阵更新做 NS 后处理。若更新矩阵的奇异值分解为

$$
M=U\Sigma V^\top,
$$

理想化的正交化方向与 \(UV^\top\) 有关；实际使用有限步多项式迭代，不能直接当作精确 SVD 的结果。原始 Muon 的系数设计也不要求每个奇异值都精确收敛到 \(1\)。[Muon 原始说明](https://kellerjordan.github.io/posts/muon/)

你应能读懂下面这一类迭代：

$$
A_k=X_kX_k^\top,
$$

$$
X_{k+1}=a_kX_k+\left(b_kA_k+c_kA_k^2\right)X_k.
$$

重点不是背系数，而是解释：

- 初始归一化在控制什么？
- 这个矩阵多项式如何作用于奇异值？
- 为什么不同系数和迭代步数会影响速度、精度与稳定性？
- 为什么先根据长宽关系决定是否转置？
- 为什么不能对任意 row shard 独立做 NS，再拼回去？

最后一个问题尤其关键：**NS 包含矩阵乘法，完整矩阵中的跨分片关系通常不能由各 shard 独立计算保留。**

做一次形状和计算量推导。设转置处理后的输入为 \(X\in\mathbb{R}^{r\times c}\)，且 \(r\le c\)，则：

- \(XX^\top\) 的形状为 \(r\times r\)。
- \(A^2\) 的形状为 \(r\times r\)。
- \(AX\) 的形状为 \(r\times c\)。

按一次乘加计两个 FLOPs，主要矩阵乘法每轮约为：

$$
4r^2c+2r^3.
$$

这直接解释了你的 **owner 成本估计为什么不宜只看元素数量**：元素数量相同的两个矩阵，长宽比不同，NS 成本可能相差很大。

**达标问题：**

- Muon 是在正交化权重、梯度，还是动量形成的更新？
- 矩形矩阵可以同时满足 \(Q^\top Q=I\) 和 \(QQ^\top=I\) 吗？
- 秩亏或全零输入有什么特殊性？
- “每 rank 六次 NS 变两次”与“总计算量下降”是什么关系？

**小练习：**

**学习模块 D：PyTorch 张量存储、临时张量与 BF16**

这一部分对应 BF16 前置、接收缓冲区复用、NS 临时张量复用，以及 FP32 分配 `9→1`。

需要掌握：

- `shape`、`stride`、`storage_offset`、contiguous。
- `view()`、`reshape()`、`transpose()`、`contiguous()`、`clone()` 的区别。
- 共享存储和别名：修改一个 view，可能修改其他张量可见的数据。
- 原地运算与 `out=` 的适用条件、读写依赖。
- Python 引用释放、存储复用与 CUDA caching allocator 的关系。

`view()` 共享已有存储；`reshape()` 是否复制取决于布局。因此，“写了 `reshape()`”不能作为消除拷贝的证据。[Tensor Views 官方文档](https://docs.pytorch.org/docs/stable/tensor_view.html)

精度方面需要理解：

- FP32、FP16、BF16 的指数和有效精度差异。
- 存储 dtype、计算 dtype、累加 dtype 不一定相同。
- 转换 dtype 本身也可能分配新存储并产生读写。
- 浮点加法不满足结合律，分布式归约顺序变化可能改变末位结果。[PyTorch 数值精度说明](https://docs.pytorch.org/docs/stable/notes/numerical_accuracy.html)

这里有一个非常适合面试深入讲的区分：

> **把 FP32 NS 改成 BF16 NS**，与**原本就使用 BF16 NS，只把 cast 移到 gather 之前**，是两件不同的事。

如果 gather 只搬运和拼接数据，前后对相同元素做相同转换，中间没有其他运算，那么可以分析两条路径的 NS 输入是否逐元素一致。不要把“转换前置”笼统解释成一次新的精度牺牲。

**学习模块 E：集合通信、同步协议与成本模型**

先能手画三张卡上的数据流，再学习性能模型。

| 通信操作 | 核心语义 | 在项目中的联系 |
|---|---|---|
| `all_reduce` | 归约后，各参与 rank 得到结果 | 梯度存在性、范数平方和 |
| `all_gather` | 各参与 rank 得到所有分片 | 重建完整 NS 输入 |

需要能区分“拼接”和“求和”：NS 输出已经在 owner 上算完后，回传切片通常是在分发结果，不能只因为名字里有 scatter 就认为必须使用 `reduce_scatter`。集合通信语义可对照 [NCCL 官方说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)。

**学习模块 G：MuonH 回缩与分片归约的等价条件**

这一部分必须以你的代码为准。仅凭“MuonH”“Hyperball 回缩”还不能确定更新公式。

先从实现整理出准确顺序：

**动量更新 → NS → 更新归一化或缩放 → 候选权重 → 回缩 → 写回。**

确认：

- 每一步的输入输出。
- 范数作用于整张矩阵、每个 head，还是其他分组。
- 目标范数如何确定。
- 权重衰减放在哪里。
- 哪些步骤使用 FP32。
- 零范数如何处理。
- 回缩是否影响优化器状态。

然后学习：范数约束、投影到球内、缩放到球面、回缩之间的区别。不要在没有公式的情况下把它们混为一谈。

你的分片回缩优化可以围绕一个核心恒等式理解。若候选权重 \(C\) 被互不重叠且完整覆盖的 shard 划分：

$$
\|C\|_F^2=\sum_{r=0}^{p-1}\|C^{(r)}\|_F^2.
$$

因此，**若回缩所需的全局信息只有这些范数统计量**，就有机会通过小型归约得到缩放系数，再在各 shard 本地应用，无需收集完整权重。

需要逐项审查：

- 是否重复计入 HSDP 副本？
- 是否包含 padding？
- 逐 head 回缩是否需要一组平方和，而不是一个标量？
- 本地候选权重是否与完整路径完全对应？
- 归约顺序和累加精度带来多大差异？

**达标问题：**

- 为什么这一步可以分布式计算，NS 却不能任意按 shard 分开？
- “数学上等价”与“浮点逐位一致”有什么区别？
- 哪种回缩公式不能只靠平方和完成？
- 为什么当前实现把分片回缩作为可选开关？

**学习模块 H：NS owner 调度与结果分片回传**

- owner 选择与成本估计。
- 按矩阵个数均分和按计算量均分的差异。

把收益和新增开销同时考虑：

$$
\text{净收益}
\approx
\text{消除的重复 NS 时间}
-
\text{新增通信、打包及等待时间}.
$$

这是分析框架，实际以测量为准。

> 如果后续所有操作都能通过本地切片和少量全局统计量完成，就不需要让每个 rank 持有完整 NS 结果。

这解释了为什么它能和分片回缩组合，也解释了为什么不能孤立地删除完整结果回传。

针对临时张量复用，准备：

- 每个缓冲区何时可覆盖。
- 是否仍有其他 view 引用它。
- 是否仍有异步操作在使用它。
- 输入输出别名是否满足算子要求。
- 提前释放跨参数引用，缩短的是哪一段存活时间。

针对 AdamW fallback，准备：

- 参数、梯度和状态的布局匹配条件。
- 哪些情况回退到原路径。
- 原地修改本地 tensor 如何反映到参数存储。
- `torch.no_grad()` 的作用。
- 与 `foreach`、fused AdamW 的关系：它们减少的开销层次是否相同。

**达标问题：**  
“如果 CPU dispatch 已经显著减少，但 GPU 训练时间几乎不变，你怎么解释？”

答案应回到实际瓶颈：原来的 CPU 开销可能被 GPU 执行覆盖，也可能优化器阶段主要受通信或大矩阵计算限制。

**学习模块 J：性能分析、正确性验证与证据表达**

这是所有模块最后都要落到的地方。

性能测量要掌握：

- CPU wall-clock、CUDA Event、Profiler 区间各自测到什么。
- CUDA 异步执行为何会让普通计时产生误判。
- warmup、首次状态初始化、缓存建立与稳态测量。
- 多 rank 平均值、最大值、波动与长尾。
- 通信和计算存在重叠时，为什么各分项时间不能直接相加。
- 同步点会不会改变原本的重叠行为。

GPU 执行与同步语义参考 [CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html)；时间线、算子和内存分析参考 [PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html)。

正确性验证建议分四层：

| 层次 | 主要验证内容 |
|---|---|
| 算子级 | NS、候选权重、范数和回缩结果 |
| 单步优化器级 | 参数、动量、AdamW 状态及计步 |
| 多步训练级 | 误差积累、loss、梯度范数、异常值 |
| 完整训练级 | 收敛质量、吞吐、稳定性与资源占用 |

测试布局至少考虑：不等长 shard、空 shard、非连续张量、完整本地块、跨 rank 块、复制布局、部分梯度缺失。

性能验证则要做消融：分别开启各项优化，再测试关键组合。**不能把各项独立收益直接相加**，因为它们可能消除的是同一段开销，也可能把瓶颈转移到别处。

你的结果需要按证据范围分别表达：

| 现有数字 | 能支持的结论 |
|---|---|
| `7.862 s`、`78.2%` | 基线中优化器区间值得重点分析；分母需准确说明 |
| gather 次数下降 | 指定布局和配置下，某类通信调用减少 |
| 每 rank NS `6→2` | 指定调度下，每 rank 重复计算减少 |
| payload 减少 50% | 按已定义口径计算的逻辑数据量减少 |
| FP32 分配 `9→1` | 隔离更新中新存储分配次数减少 |
| CPU `0.50→0.11 s` | 指定宿主基准中的开销下降 |

**达标问题：**

- 优化器区间是否包含等待先前 CUDA 工作完成的时间？
- 少量 rank 的 Gloo 正确性验证，能证明哪些问题，不能证明哪些性能结论？
- 目前是否已有优化后的 64 卡端到端结果？
- 如果没有，下一组最有价值的实验是什么？
