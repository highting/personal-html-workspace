# 内容制作工作区约定

本页统一约定材料入口、分类、命名、版本和交付。日常制作复用已经调整好的模板和约束，只有用户明确要求时才修改公共模板。学习、博客与汇报的具体制作步骤见[四场景流程](content-workflow.md)；3:4 图片和发布配文要求仅用于小红书。

## 日常使用

日常只用一个投放入口：`inputs/待分类/`。把新笔记文件或完整文件夹拖进去，然后在本项目会话中说“处理新材料，做成学习长文”（也可指定博客、汇报、小红书，支持一次选择多种）。代理负责识别主题、整理分类、套用现有模板、检查和交付；用户无需预先分类、命名成品、填写配置或运行脚本。

单文件可以直接放在 `待分类/` 下；带配图、附件或相对链接的笔记应拖整个文件夹。代理先检查本次新材料：单文件建立主题目录，完整文件夹保留内部结构，再归入 `inputs/<内容分类>/<主题>/`。本流程授权整理本次待分类材料，整理时不改正文、不覆盖同名文件、不拆散配图引用；同名目标已存在时先比较内容，无法确定是否为改版则询问。已归档的其他原稿不顺手迁移。无法判断分类的主题继续留在 `待分类/<主题>/`，不妨碍制作。

新材料统一进入 `inputs/`，包括小红书材料；已有 `blogs/<分类>/<主题>/` 原地兼容使用，不要求迁移或重复复制。主题名可用中文和空格。同一份材料只保留一个主题目录，可以反复制作不同场景。

| 内容分类 | 存放内容 |
|---|---|
| `机器学习` | 概念、算法、推导与学习笔记 |
| `论文阅读` | 以论文精读或论文对比为主的材料 |
| `工程实践` | 项目实现、调试、工具与工程经验 |
| `待分类` | 尚未确定归属的材料 |

代理按材料的主要目的选一个分类，不在多个分类复制同一原稿；用户也可直接放入已知分类，沿用该分类。分类可新增，也可按需要分子类。输入按内容归属分类，输出用场景区分用途。

例如，拖入时：

```text
inputs/
└── 待分类/
    └── Hyperball/
        ├── main.md
        └── images/
            └── geometry.png
```

代理阅读后归类，下面仅为归入“机器学习”的结构示例，实际分类由材料决定：

```text
inputs/
└── 机器学习/
    └── Hyperball/
        ├── main.md
        └── images/
            └── geometry.png
```

在本项目中新建或继续会话，通常只需说：

> 处理待分类里的新材料，做成学习长文。

> 处理新材料，同时做成博客和汇报。

已经归档的主题可以直接点名：

> 把 inputs/机器学习/Hyperball 做成学习长文，复用本项目当前模板和约束，输出到 Hyperball-学习。

> 把 Hyperball 写成技术博客，保留关键推导与来源，输出到 Hyperball-博客。

> 用同一份 Hyperball 材料做面向组内同事的 15 分钟技术汇报，输出到 Hyperball-汇报。

> 把 Hyperball 做成小红书图文，正文用 HTML 排成图片，辅助图用 HTML＋SVG，输出到 Hyperball-小红书。

主题名在 `inputs/` 和 `blogs/` 中唯一时可以只说名字；重名时提供分类或完整相对路径。用途沿用已明确的场景，无法判断时才询问；未指定辅助图模式默认 HTML。拖入本身不会触发生成，需要在会话中发出要求。自动读取这些约定的前提是会话工作目录在本项目中。

也可以在会话中提供文件、粘贴笔记或给出本地路径，并说明“将材料收进本项目并制作”。代理先把可访问材料复制或保存到对应主题目录，再制作；分类不明确时先放 `待分类`。外部原文件不移动，同名文件不静默覆盖，附件无法访问时如实说明。链接材料保留来源，缺少关键正文时不凭主题名编造。

## 成品命名与分类

新成品统一使用 `<主题短名>-<场景>`，避免同一主题的不同用途共用一个入口：

| 用途 | scene | 成品目录示例 | 打开或使用 |
|---|---|---|---|
| 个人学习 | `learning` | `output/Hyperball-学习/` | `index.html`，连续长文 |
| 技术博客 | `blog` | `output/Hyperball-博客/` | `index.html`，连续长文 |
| 技术汇报 | `report` | `output/Hyperball-汇报/` | `index.html`，含讲者备注；`page-01.png` 等逐页图片 |
| 小红书图文 | `rednote` | `output/Hyperball-小红书/` | `预览.html`；同层图片、`标题.txt`、`配文.txt` |

不同分类有同名主题时加分类限定，例如 `机器学习-优化器-学习`。明确保留两套方案时再加方案后缀，例如 `Hyperball-小红书-HTML`、`Hyperball-小红书-生图`。只请求辅助图或一图流时用 `主题-辅助图`、`主题-一图流`，不扩成整篇。不要用 `最终版`、`新版`、`test` 等泛名。

已有成品继续沿用原入口，例如 `output/Hyperball/`、`output/Hyperball-阅读版/`；修改时从原 `run.json` 核对来源和场景，不仅凭名称推断。新做独立场景使用新的规范名称。

准备脚本省略 `--name` 时仍使用主题文件夹名；**代理必须显式传入按本页确定的成品名**。准备和交付前均核对输入路径、场景、方案与成品路径。已有路径属于另一主题或场景时换名，不能因为发布脚本允许替换就覆盖。

`output/index.html` 的正式成品按“内容分类 → 主题 → 场景”归组，示例成品、工作版本、历史归档、运行环境分开。每次交付时由代理同步对应条目并核对链接；当前发布脚本不会自动更新总览。总览用于导航，输入路径与 `run.json` 用于追溯；未知的历史分类或来源不凭名称编造。

## 输入与正文选择

推荐正文名 `main.md`，也支持保持现有文件名。准备脚本优先识别主题根目录的 `main.md`、`article.md`、`index.md`（按此顺序）；否则寻找唯一的 Markdown、Word、PDF 或 HTML 正文。已知主稿时显式传 `--entry`，路径相对于主题文件夹。存在多份候选时先阅读判断，确实无法判断才询问；辅助说明与论文附件不应误当主稿。

Word、PDF、HTML 输入先用对应工具读取，并将供渲染的 Markdown 整理到工作目录的 `work/`。准备脚本不负责格式转换、排版或生图。完整正文不可误当作图片附件忽略。图片引用到文件夹外部时，应在 `work/` 中补齐资源并调整工作稿引用；交付资源必须能离开原机器使用。

## 目录与版本

```text
项目根目录/
├── inputs/                        # 新材料：内容分类/主题/正文和附件
├── blogs/                         # 已有原稿兼容入口，不重复复制
├── output/
│   ├── Hyperball-学习/            # 学习长文，打开 index.html
│   ├── Hyperball-博客/            # 博客长文，打开 index.html
│   ├── Hyperball-汇报/            # 演示 index.html 与逐页 PNG
│   ├── Hyperball-小红书/          # 小红书成品示例
│   │   ├── 标题.txt
│   │   ├── 配文.txt
│   │   ├── card_1.png             # 按页序放完整图片，不再多套 images/
│   │   ├── card_2.png
│   │   ├── 预览.html              # 同页展示标题、配文和图片
│   │   └── html/                  # 可离线打开的 HTML 排版源页及资源
│   ├── _work/<成品名>/
│   │   └── <时间戳>-<场景>-<模式>/
│   │       ├── source/            # 原始材料快照，不修改
│   │       ├── work/              # 正文排版稿、SVG、图面说明和检查材料
│   │       ├── delivery/          # 本次成品暂存，不作为日常入口
│   │       ├── previous-deliveries/ # 更新短路径前保留的旧交付（如有）
│   │       ├── run.json           # 输入、路径和执行状态
│   │       └── delivery.md        # 来源、页序和检查记录
│   ├── _archive/                  # 整理前的产物和检查材料
│   ├── index.html                 # 本地分类总览，成品与历史材料的统一入口
│   ├── validation-python/         # 已有本机验证依赖
│   └── validation-browsers/       # 已有本机验证浏览器
├── demos/                         # 主题和图形示例
├── assets/                        # 公共模板、主题、KaTeX
├── prompts/                       # 公共约束与场景提示词
├── scripts/                       # 准备和渲染脚本
├── references/                    # 长期流程说明
├── skills/                        # 插件入口
└── tests/                         # 回归测试
```

学习、博客、汇报的成品结构按上表；长文不强制生成标题与配文。小红书两种模式均将完整 PNG 序列、标题与配文放在成品目录同一层，HTML 源页放 `html/`。原 `prepare_blog.py` 工作目录时间戳只带模式，已有路径保留。检查器可能随成品保存 `qa.json`、`checks/` 等验收证据，它们不是阅读入口。

每次新请求在 `_work/` 下建立独立工作目录，同次修正复用它。已交付后的再次改版新建工作目录，需要沿用上一版工作稿时记录所继承版本；原稿更新后重新读取材料并建立快照。新的结果检查通过且实际查看后才更新短路径；现有成品先留存到本次 `previous-deliveries/`，再整体替换，避免混入旧图。失败或未验证的新版本留在工作目录，保留上一份已检查成品。小红书两套比较共用正文 PNG、HTML 源页、页序与配文，只替换辅助图。

例如：“修改 output/Hyperball-学习 的第二节，补充数值例子，检查后更新同一入口并保留旧版”；或“我更新了 inputs/机器学习/Hyperball/main.md，请重新生成 Hyperball-学习”。不直接改成品后跳过验收。

## 代理执行约定

收到“处理新材料”时，先检查 `inputs/待分类/` 中尚未制作或有更新的材料，并结合已有 `run.json` 核对来源和快照，避免仅因文件仍在待分类目录就重复制作；不需要后台监听。归类本次材料后，确定输入路径、主稿、场景、成品名并检查冲突，再创建工作副本。用途沿用本次要求或已明确上下文，没有用途时一次询问学习、博客、汇报、小红书中的一项或多项，不自动生成全部四种。已知信息不重复确认。学习、博客与汇报按[四场景流程](content-workflow.md)准备、构建、检查和汇总：

```powershell
python -X utf8 scripts/prepare_content.py "inputs/机器学习/Hyperball" --entry main.md --scene learning --name Hyperball-学习
```

小红书日常新建工作目录同样用 `prepare_content.py`，兼容 `inputs/` 和已有 `blogs/`，传 `--scene rednote --name Hyperball-小红书`，保存共同与场景Prompt，之后使用原卡片渲染器。详细参数与检查按场景流程执行，不用示例文件名替代实际主稿。在 `delivery.md` 中记录内容分类、主题、输入路径、场景、成品名、主线、来源和真实检查结果；保留 `run.json` 原字段。汇总后更新分类总览，并直接交付成品链接。这里的“发布”仅指本地汇总，不上传网站或社交平台。

### 小红书执行入口（含已有 blogs 材料）

先确定博客和正文，再从项目根目录运行（Python 不在 PATH 时使用当前环境提供的解释器绝对路径）：

```powershell
python -X utf8 scripts/prepare_content.py "blogs/机器学习/Hyperball" --entry main.md --scene rednote --mode html --name Hyperball-小红书
# 多正文时明确入口，路径相对于博客文件夹
python -X utf8 scripts/prepare_content.py "blogs/机器学习/Hyperball" --entry "正文/技术稿.md" --scene rednote --mode images --name Hyperball-小红书-生图
```

脚本返回 `run_dir`（独立工作目录）、`artifact_dir`（本次成品暂存）、`delivery_dir`（简短交付入口），并复制完整博客目录到 `source/` 和 `work/`，保持内部相对引用。使用 `work_entry` 作为工作稿入口；转换格式后在 `run.json` 更新该字段。

两种模式均先整理能独立读完的正文，规划正文页和辅助解释图。正文渲染稿准备好后运行渲染器，输出到本次 `artifact_dir`，分批渲染也可先放 `work/` 再按共同页序汇总：

```powershell
python -X utf8 scripts/rednote_render.py "<work_entry>" --math katex --save-html -o "<artifact_dir>"
```

最终图片按页序命名为 `card_N.png`（明确需要独立封面时可加 `cover.png`）。生图模式只对非正文视觉调用相应工具；分批生成不能覆盖其他页。HTML 页及资源放在 `artifact_dir/html/`；正文排版稿、图面说明和提示词留在 `work/`。按[发布标题与配文规则](content-plan.md#发布标题与配文)写好 `artifact_dir/标题.txt` 和 `artifact_dir/配文.txt`：标题不使用第一人称，直接表达主题或核心论点；配文用作者第一人称，轻松自然且只作摘要。工具生成文件必须本地化。

准备后 `run.json` 状态为 `prepared`，制作时改为 `generating`；完整正文图片、辅助图、标题和配文完成检查后才标记 `completed`。记录各页类型、制作方式和实际检查结果，来源与页序放在工作目录的 `delivery.md`。然后执行：

```powershell
python -X utf8 scripts/publish_content.py "<run_dir>"
```

脚本生成包含标题、配文和图片的 `预览.html`，将成品整体汇总到 `delivery_dir`，并更新交付记录。`prepare_blog.py` 与 `publish_blog.py` 仅兼容历史调用和工作目录；旧记录可继续由 `publish_blog.py` 汇总，不要求重建。最终回复优先链接 `output/<短名>/`、`标题.txt`、`配文.txt` 或 `预览.html`，不要把中间 `work/` 路径作为发布材料入口。仅请求辅助图或一图流时按用户范围准备交付文案，不扩写整篇正文。

## 历史材料与维护

早期的 `hyperball-xhs`、主题产物和 HTML 检查材料在 `output/_archive/2026-09-14/`；旧版本仍可保留在 `output/blogs/`，不再将该深层路径作为新的交付入口。其中 `hyperball_xhs.md` 是已有改写稿，不自动当作博客原稿。历史检查脚本只是当时的复现材料，内部旧路径执行前需调整；已有版本可补上 `delivery_dir` 后用汇总脚本建立短路径成品。

本地分类入口为 `output/index.html`。2026-10-03 将独立模板预览、HTML 转 PNG 验证与暖色背景验证移入 `output/_archive/2026-10-03/checks/`，迁移清单与原文件哈希在同级 `organization.json`。`_work/` 与 `output/blogs/` 中仍被 run、交接和错题本引用的历史版本保留原路径，通过总览分类。早期静态模板归入 `assets/legacy/`，早期示例稿归入 `demos/legacy/`；当前模板、主题和示例入口保持不变。

已有验证依赖暂存位置保留，避免破坏当前可用环境。后续新依赖遵循 `references/environment.md`，使用用户环境或 `.venv/`，不要继续混入正式产物。

`output/` 已被 `.gitignore` 忽略；`inputs/` 与 `blogs/` 原稿可纳入版本管理。Git 忽略不等于备份：长期备份应覆盖原稿、需要保留的工作版本和短路径成品。公共模板和主题统一维护，单篇内容在其工作目录处理，不放进公共工具目录。维护模板是独立任务，不随内容制作顺手修改。
