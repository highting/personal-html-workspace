# 四种场景的策划与验收

## 个人学习 learning

按[学习 Prompt](../prompts/scenes/learning.txt)覆盖主题内的核心、必要前提与直接相关知识，按概念依赖组织连续长文，默认比同主题博客讲得更广、更细。用直白语言、贯穿例子和必要推导讲清对象、操作、原因与条件；涉及张量时说明关键形状变化及作用，不逐句翻译代码。不能自行收窄为少数论点，或用延伸阅读代替相关知识的实质解释；也不递归补齐整个学科。验收看读者能否不返回原稿就解释核心关系、跟随过程并完成简单应用或变化判断，不能只复述术语与结论。

主要优化文稿质量与有效图片密度，按重要解释任务核对图解覆盖，尤其检查后续章节和新引入的机制，不能只看全篇图数。HTML复用分层目录、阅读宽度和章节间距，检查首屏、章节交界、图解、公式、代码及结尾；验证目录、进度和主题切换。默认交连续HTML，检查截图不是正文长图。

## 技术博客 blog

按[博客 Prompt](../prompts/scenes/blog.txt)围绕具体知识点简明讲清原理，开篇交代问题与核心判断，用必要解释、图解、例子或证据接通关键关系。只就近补足必需前提，不主动扩展为知识综述、变体大全或学习教程；必要理由与条件仍保留。标题直接表达主题，不制造悬念。保留连续段落；来源靠近所支持的论断，真实证据和教学构造分开。作者、日期、经历只写实际给出的信息。

主要优化文稿质量与有效图片密度，图解覆盖核心机制、关键转折与最终比较，不能只集中在开篇。HTML与学习共用阅读模板，解释深度与覆盖范围按博客目标取舍，不把学习稿直接删短。检查每段、每图是否帮助回答开头的问题，以及图文衔接、来源、明暗呈现和结尾；不另设独立版式，不强制小红书标题/配文。

## 技术汇报 report

首先优化视觉效果，其次校准文稿重点与详略。按[汇报 Prompt](../prompts/scenes/report.txt)确定听众需要形成的判断：成果汇报讲改变、结果与意义；进展汇报讲实际产出、障碍与下一步验证；方案评审讲约束、取舍和建议；论文/技术分享讲问题、机制、作者证据与局限。尽早给出本次重点，背景与方法按支持主线的需要取舍，不默认全部写成个人成果。

完整稿按页或页组组织“要表达的判断—证据或图面—必要条件—口头解释与衔接”，而非将长文章切页。观众页能快速读懂主信息，备注补足怎么看、为什么及前后连接；重要条件仍在观众页。一个讲解任务可跨多页，视觉焦点可以是图表、机制图或明确结论，不强制每页配图。有实际待决事项才提出确认请求。全部文案都应属于实际汇报，制作提醒、资料缺口和会前待办只留工作记录。

默认1280×720、纯白背景，HTML只提供纯白/纸白背景选择，切换保留当前页；不提供深色或明暗样张。目录可直达，←/→及PageUp/PageDown翻页，Home/End到首末页。备注默认收起，按钮或N主动切换，Esc收起备注与目录；展开的备注在当前页面可见，导出PNG始终隐藏。逐页逐句审读全部文案与备注，再查看主要信息能否迅速辨认，以及证据联系、布局重心、安全区、页脚、图内字号和条件；交付白底PNG，并核对纸白背景下的可读性。

## 小红书 rednote

首先优化最终图片的视觉效果，其次校准选题与文稿详略。按[小红书 Prompt](../prompts/scenes/rednote.txt)围绕小主题，用图形承担关键关系、短而连贯的文字补足原因和条件；纯文字页仍可使用，但不能仅靠分栏代替对照关系的呈现。图片内完整的是所选问题的解释，可略难推导，不能略理由和条件；过量先删旁支，必要解释仍放不下再按语义增页，配文只作摘要。沿用[原小红书流程](rednote-scene.md)，纸白academic、3:4、1080×1440 CSS px、DPR2。先检查整组重点与节奏，再逐张核对原图和390px预览的可读性；不设固定图文面积比例。只图请求按指定范围执行。
